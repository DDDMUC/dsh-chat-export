### 2.3 关键校验：宿主实测 ≡ 离线解码

同一份日志用两条完全独立的数据路径渲染，逐字节比对：

- **宿主路径**：`GET /api/dsh-chat-export.export`（走 `ctx.sessionPersistence`）
- **离线路径**：自己逐帧解 `session.v3.jsonl.zstd` 后调 `produceExport`

| 场景 | 结果 |
| --- | --- |
| 默认 Markdown | ✅ 字节完全一致（4,373,557 字节） |
| `--thinking` | ✅ 字节完全一致（6,415,575 字节） |

这条比对同时说明：多帧 zstd 解码器与官方持久化服务读出来的日志**内容一致**，

## 8. DSH 0.1.7-rc.2 的会话读取断裂与兜底

升级到 0.1.7-rc.2 后发现：**两个会话在官方导出和我这边同样 500。**

| 会话 | 官方 `session-log-export` | 我（加兜底前） |
| --- | --- | --- |
| `session-5e6c2afd`（v3+v4 已封存一致） | 200 | 200 |
| `session-5ce30467`（仅 v4，新） | 200 | 200 |
| `session-62778e99`（仅 v4，新） | 200 | 200 |
| `session-c2134ed8`（v3+v3+v4） | 200 | 200 |
| `session-48310605`（v3 封存 + v4 追加） | **500** | **500** |
| `session-e81f9424`（v3 封存 + v4 追加） | **500** | **500** |

两个坏会话的共同点：**v3 已 `session/end-seed` 封存，v4 又在它之后追加了新事件**；
v3/v4 内容一致的会话则正常。官方报 `session log export failed to read the stored log`。

### 修法

给读取链加了**第四层兜底**：直接读会话文件，用插件自己的多帧 zstd 解码器。
`readSessionLog` 现在是：

1. `sessionPersistence.open(id, 'read')` —— 官方主力路径
2. `sessionQuery.readSession(id)`
3. `sessionQuery.readSurface(id)`
4. **`readArtifactDirectly(id)`** —— 绕过服务层，直接逐帧解 `session.vN.jsonl.zstd`

同时修了两个自己的 bug：

- **错误汇总只报最后一个 attempt**，把根因藏了（报的是 fallback 末端的
  `session "…" not found`，而真正失败的是 persistence read）。现在所有 attempt
  的原因都会报出来。
- **`newestGeneration` 的正则捕获组带了 `v` 前缀**，`Number('v4')` 是 NaN，
  导致永远选不出最新世代。

兜底后实测：即使四个服务全部抛错，两个坏会话仍能完整导出
（v4 全量、缺图 0）。

### 引擎仓库不接受 issue

想报上游时确认过：`deepseek-ai/deepseek-harness` **issues 是关闭的**，
`zhu1090093659/dsh-web` 虽开着但那是插件索引 / Web UI 仓库，装不了引擎的读取回归。
所以兜底留在插件里就是最终答案 —— 也没有别的渠道。

### 别再踩的两个坑

- **`DSH_HOME` 不能写死成 `~/.dsh`。** 本机 `DSH_HOME` 是设了的，官方
  `dsh-base` 的 persistence 用的是 `root: !!js dshHomePath('sessions')`。
  兜底改为同一套解析（`DSH_HOME` 优先、`~` 展开、否则 `~/.dsh`），
  并且把字面 `"undefined"` / `"null"` 当作未设置 —— 包装脚本常误设这两个值，
  照做会让每个会话都藏进一个不存在的目录。
- **`dshHome()` 的 env 必须可注入。** 第一版测试直接改 `process.env.DSH_HOME`，
  在 vitest 并行跑多个测试文件时会互相污染。现在签名是 `dshHome(env = process.env)`，
  测试注入自己的 env。

## 10. 修复「仅当前上下文」漏出被压缩的内容

用户问「完整日志 / 仅当前上下文」是什么意思，顺手核对时发现 **surface 模式没有真正生效**。

现象：本会话 `full` 与 `surface` 的**用户消息数完全一样（27 / 27）**，
但 `foldSurface` 明明标记了 28 条 `user/message` 被压缩遮蔽。

### 根因

同一条用户消息在日志里有**两份**：

| seq | 类型 | surfaceOp | 被遮蔽 |
| --- | --- | --- | --- |
| 617 | `agent/inbox/spliced` | 无 | 否 |
| 623 | `user/message` | `append` | **是** |

压缩（seq 3198，`replace` 覆盖 8..2117）遮蔽的是 `user/message`，
但 **spliced 那份没有任何 surfaceOp，永远不会被标记遮蔽**。
而我的 spliced 副本是「先入队、到回合边界再释放」的，释放时对应的
`user/message` 早已被 surface 丢弃 —— 它的 id 从没进过去重集合，
于是 spliced 副本赢了，被压缩掉的内容又冒了出来。

### 修法

用**durable message id** 作为两份记录的连接键（这也是去重本来就用的键）：
先算出所有「被遮蔽事件携带的 message id」，`pushUserEntry` 里直接拦住。

修复效果（真实会话）：

| 会话 | 用户消息 full → surface（修复前） | 修复后 |
| --- | --- | --- |
| 本会话 | 27 → 27 | 27 → **15** |
| 长会话 | 94 → 94 | 94 → **72** |
| 短会话 | 1 → 1 | 1 → 1（无用户消息被压缩） |

判定用的硬指标是「被遮蔽的 message id 里，有几个仍作为 user 条目渲染出来」——
修复前 10 条，修复后 **0 条**。

> 一开始我用「正文文本是否出现在导出里」当探针，得到 5 条残留，逐条追查后
> 确认**全是误报**：压缩摘要本身会引用被压缩的原文，而且同一句话可能还有
> 另一条未被遮蔽的消息（例如压缩后被重新投递的副本）。文本不是身份，id 才是。

回归测试 `keeps a compacted prompt out of the surface even when the inbox still carries it`，
并且**验证过撤掉修复它会失败**。

写这个用例时还踩了一下：`replace` 的锚点必须落在**有 surfaceOp 的节点**上，
我把 `startSeq` 写成了 spliced 事件（无 surfaceOp），整个替换被防御性跳过，
用例于是在「修复已生效」的情况下依然失败 —— 是用例的问题，不是实现的问题。

## 11. 默认内容改为「对话本身」（第四轮）

用户要求默认勾选【用户输入】【模型输出】【思维链】【系统提示词】，
并明确「工具调用与结果」**默认不勾**。

| 选项 | 旧默认 | 新默认 |
| --- | --- | --- |
| 思考块 | 关 | **开** |
| 系统提示 | 关 | **开** |
| 工具调用与结果 | 开 | **关** |
| 注入内容 | 关 | 关（不变） |
| 时间戳 / 用量 | 开 | 开（不变） |

用户输入与模型输出本来就没有开关，始终导出。

### 差点漏掉的耦合

改完宿主默认值后**10 个测试失败** —— 但更要紧的是：`src/client.js` 里有一份
**独立的 `defaultForm()`**，对话框用它渲染开关的初始位置，而宿主用
`defaultOptions()` 填补请求里没带的键。**两份不一致，界面显示的和实际导出的就是两回事**，
而我只改了宿主那份。

两个 bundle 无法互相 import，所以补了一个**默认值一致性测试**：
从 `client.js` 源码里解析 `defaultForm()`，逐键与 `defaultOptions()` 比对，
并要求键集合完全相同。**验证过故意让客户端漂移会失败**
（把客户端 `tools` 改成 `true`，测试报 `tools: expected false to be true`）。

顺带修了 10 个「本来就依赖旧默认」的用例 —— 它们测的是工具渲染，
现在显式写 `tools: true`，用例意图反而更清楚了。

### 顺序核对

新默认下系统提示会渲染出来，位置在**第一条用户消息之后**。一度怀疑是排序 bug，
核对事件序号后确认是对的：

```
seq 3  agent/inbox/spliced   ← 收件箱收到用户消息
seq 4  turn/start            ← 回合开始，释放上面那条
seq 7  system/message        ← 这一步才组装系统提示
```

用户确实先说话，系统提示是为第一次模型调用才组装的。渲染忠于日志顺序。

## 12. 「默认勾选四项」的实际含义（第五轮）

上一轮我把用户的要求理解成「默认内容 = 对话本身」，于是只打开了思考块与系统提示，
并告诉用户「用户输入与模型输出本来就没有开关」。**用户重复了一次要求，说明我理解错了** ——
他要的是**这四个都是可勾选的项，且默认勾上**。

于是把前两项做成真正的开关：

| 开关 | 宿主字段 | 默认 |
| --- | --- | --- |
| 用户输入 | `userInput` | ✅ |
| 模型输出 | `modelOutput` | ✅ |
| 思维链（原「思考块」） | `thinking` | ✅ |
| 系统提示词（原「系统提示」） | `system` | ✅ |
| 工具调用与结果 | `tools` | ❌ |
| 注入内容 | `injected` | ❌ |
| 时间戳 / 用量统计 | `timestamps` / `usage` | ✅ |

- 标签改用用户的原话：「思考块」→**思维链**、「系统提示」→**系统提示词**；四项排在最前。
- 关掉某一项会真的不导出：`options.userInput === false` 时 `pushUserEntry` 直接返回，
  `options.modelOutput === false` 时跳过 `assistant/message`。实测（真实会话）：

  | 设置 | 渲染出的条目 |
  | --- | --- |
  | 默认（四项全开） | `turn 1 · user 1 · system 1 · assistant 50 · tool 85` |
  | 关掉用户输入 | `turn 1 · system 1 · assistant 50 · tool 85` |
  | 关掉模型输出 | `turn 1 · user 1 · system 1 · tool 85` |
  | 只留思维链 + 系统 | `turn 1 · system 1 · tool 85` |

- 新增 `--input` / `--no-input`、`--output` / `--no-output`。
- 第 11 节那个默认值一致性测试自动覆盖了新增的两个键。

**教训**：用户第一次说「默认勾选…四个」时，我凭「前两项没有开关」就自行把要求
降级解释了，还把这个解释当成结论回复。用户重复同一句话就是信号 —— 应该照字面实现。
